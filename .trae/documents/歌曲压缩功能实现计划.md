# 歌曲压缩功能实现计划

## Context（为什么做这件事）

当前应用只有一个「消除重复音符」功能（`dedupeCurrentNotes`），只做 `tick+instrument+key` 完全去重，几乎无损。用户希望把它升级为通用的「歌曲压缩」——通过有损删除音符来大幅降低总音符数（"有损压缩"），并形象地提供**质量滑块**。原有去重 + 空洞填补被收编为压缩机制中的一个环节：

- **质量 99%** = 仅执行原「消除重复音符」逻辑（最安全、几乎无损）。

- **质量越低越激进**（20% 最狠）。

- **空洞填补/重排序不再是去重独有**，而是压缩整体拥有：每删除一批音符后立即调用现有 `dedupeReorderNotes()` 补洞。

- 整次压缩**单次可撤销**。

## 用户已确认的决策

| 决策    | 结论                                                 |
| ----- | -------------------------------------------------- |
| 滑块默认值 | **99%**（首次打开即等价于完全去重）                              |
| 算法模型  | **两种都要**，弹窗内加「算法模型」选择器（务实启发式 / 感知引擎）               |
| 菜单    | **移除**「消除重复音符」，替换为「歌曲压缩」                           |
| 补洞时机  | **每步删除后**立即补洞                                      |
| 滑块档位  | 仅 **1% / 10% / 20% / 40% / 60% / 80% / 99%** 七个离散值 |
| 低质量警示 | 质量 **< 20%** 时在滑块下方显示**黄色**提示（可能过度删除）              |

## 架构

把"算法/候选生成"放 `nbs_client.js`（纯函数、无 DOM），"UI/接线/撤销"放 `main.js`。`dedupeReorderNotes` 已在 `nbs_client.js`，保持一致。

### 统一管线（v4：两模型共用同一删除量 + 轨道分组）

```
compressSongCore(notes, q, model, ctx):
  kept = notes.slice()                 // 存活列表（对象引用）
  bucket(n): 0=不处理(完全不动) / 2=减轻处理 / 1=正常
             （ctx.excludeLayers / ctx.lightenLayers 为 layer 数组；exclude 优先）
  flushBatch(batch):
    keepSet = Set(batch)               // ★必须用 Set（引用同一性）
    kept = kept.filter(x => !keepSet.has(x))
    totalMoved += window.dedupeReorderNotes(kept, batch)
    removed.push(...batch)

  // 阶段1：完全去重（仅 正常/减轻 轨道；不处理轨道原样保留，不参与去重）
  for n in kept: if bucket(n)!=0:
    key = n.tick + ':' + n.instrument + ':' + n.key
    if seen[key]: dedupeBatch.push(n) else seen[key] = true
  flushBatch(dedupeBatch)

  // 阶段2：有损删除（按轨道分组各自配额；99% 档不执行）
  if q < 0.99:
    cnt[1], cnt[2] = 去重后各组音符数
    budget[1] = round(cnt[1] * (1 - q))            // 正常组
    budget[2] = round(cnt[2] * (1 - q) * 0.5)      // 减轻组: 删除强度减半
    order = (model=='perceptual') ? rankPerceptual(pool) : rankHeuristic(pool)
    for n in order(升序):                          // 全局统一排序, 再按各组配额取用
      b = bucket(n); if b and budget[b] > 0: batch2.push(n); budget[b]--
      if budget[1] <= 0 and budget[2] <= 0: break
    batch2 = batch2[0 : kept.length-1]             // 至少保留 1 个
    flushBatch(batch2)

  return { removed, kept, moved }
```

**关键性质**

- **删除量 = (1−Q) 比例**，语义直观：「质量 X% ≈ 保留约 X% 的音符」。1% → 删 99%，10% → 删 90%，40% → 删 60%，80% → 删 20%，99% → 仅去重。各档差异显著。

- **两种模型删除数量完全一致**，差异只在「删哪一些」：启发式用轻量规则分，感知引擎用感知分。因此弹窗的实时预估与所选模型无关。

- **轨道分组**：不处理轨道**完全不动**（连去重都不参与，可保留其内部重复音符）；减轻处理轨道仍去重，但有损删除**配额减半**。

- `dedupeReorderNotes` 每次用当前最新 `kept`；`removed` 传本批被删引用（保持原始 layer 坐标）。

- `flushBatch` 的删除判定**必须用** **`Set`（引用同一性）**；用「对象作普通对象键」会让所有对象强转为 `"[object Object]"`，导致**全部音符被删、保留 0**（已修复的严重 bug）。

- 保护策略由「硬免疫」改为**高权重打分**：底鼓/根音等不再绝对不可删，而是在低质量档位最后被删。这样 1% 才能真正达到「极简骨架 / 接近不可听」的效果（硬免疫会让低档位无法继续压缩）。

- 复杂度：`isShort`/分组 O(n log n) + 打分单遍 O(n) + 排序 O(n log n)；打击乐密度用 **tick 预排序 + 二分计数**，避免 O(n²)。

- 预估函数 `compressSongEstimate(notes, q, {lightenLayers, excludeLayers})` 使用完全相同的配额公式，只算数量不排序 → O(n)，与所选模型无关。

### 打分函数（返回按重要性升序排列的引用数组）

`rankHeuristic`（轻量规则分，基准 0.35）

- 打击乐：大鼓 0.98 / 强拍军鼓 0.90 / 弱拍军鼓 0.55 / 其余 0.38；+0.15×力度

- 旋律：根音 +0.45；三音 +0.22；五音 −0.10；八度重复 −0.25；旋律锚点（非短时值组内最高音）+0.25；低音音色 +0.25；短音 −0.12 / 长音 +0.10；强拍 +0.12 / 非次强拍 −0.05；+0.18×力度

`rankPerceptual`（感知综合分）

```
打击乐: base×0.75 + 0.25×力度 − 0.15×密度   (base: 大鼓1.00 / 强拍军鼓0.95 / 弱拍军鼓0.62 / 其他0.45)
旋律:   S = 0.35·role + 0.20·beat + 0.15·dur + 0.15·vel − 0.10·mask − 0.05·dup
role: 根音1.00 / 旋律锚点0.95 / 三音0.85 / 七音0.80 / 五音0.45 / 八度重复0.12 / 其他0.25
beat: 强拍1.00 / 次强拍0.60 / 其他0.30
dur:  短音0.20 / 长音0.80        vel: velocity/100
mask: 同 tick 音级相近(±1)且更响者存在 → 0.6
dup:  同 tick 同音级存在另一次 → 1
```

两者都对结果做 `sort(升序)`，然后取前 `budget` 个删除。

## 执行函数 `doCompressSong(quality, model)`

```
notes = state.pianoRoll.getNotes()
if notes.length < 2: alert(空提示); return
working = notes.map(copy)               // ★在副本上压缩（见下）
res = window.compressSongCore(working, quality, model, ctx={ticksPerBeat, reorder})
if res.removed.length==0: alert(未删除任何音符); return
pushUndo()                              // ★必须在压缩"之前"的状态采集
state.pianoRoll.setNotes(res.kept); state.notes = res.kept
buildNoteIndex(state.notes); updateProgressUI(); updateNoteCount()
state.pianoRoll.render(); (renderTrackPanel)
alert(结果句「删除 {N} 个音符，保留 {M} 个。上移填补 {moved} 个」)
```

**撤销正确性（重要）**：`compressSongCore` 会**就地改写音符的** **`layer`**（每步删除后补洞上移）。若把 `state` 中的音符对象直接传入，`pushUndo()→takeSnapshot()→deepCloneNotes()` 采到的是**已上移后**的层位，撤销将无法还原原始轨道。因此必须：

1. 先 `notes.map(copy)` 生成**副本**再压缩（副本被改写不影响原对象）；
2. `pushUndo()` 在 `compressSongCore` **之前**（或至少在改写原对象之前）调用，使快照记录压缩前状态；
3. 之后再用 `res.kept`（副本对象）替换 `state.notes`。

- 移除 `dedupeCurrentNotes` 的分发分支，替换为 `compress-song → showCompressSongDialog()`。

## 风险与边界

- 空项目/音符<2：进入 core 前拦截并提示。

- 稀疏/无调性：仅在同 tick 同 instrument ≥2 键时做和声删除；孤立音符不以和声规则误删。

- 骨架保护（尤其模型 B）硬约束，避免清空声部。

- 自定义音色 id>19：一律按旋律处理，打击保护不崩溃但不生效。

- 复杂度：哈希+按需要排序，O(n log n) 可接受。

### v4（第三轮：轨道选择 + 全弹窗样式统一）

**A. 歌曲压缩的轨道选择**

### v4.1（模型说明与提示）

**为什么切换算法模型时「预计删除」不变（设计使然，非 bug）**
两个模型删除的**数量完全相同**，差异只在**保留哪些音符**（启发式用规则分，感知引擎用感知分）。预估显示的是数量，故不随模型变化。已用回归断言固化：28 个真实 NBS × 6 个非 99% 档位 = **168/168 组合的删除集合互不相同**（脚本新增断言「两模型删除集合在所有(文件,档位)组合下均不同」），确保「选模型」始终有实际意义。

**模型说明文案**

- 「算法模型」`<select>` 下方新增一行常驻说明：「两种模型删除的音符数量相同，区别在于保留哪些音符；感知引擎更贴近听感。」

- `<select>`（及两个 `<option>`）带悬浮提示，分别解释两种模型的打分维度与速度差异（9 语言本地化）。

**顺带修复的两个提示系统问题**

1. `custom_dropdown.js`：`<select>` 会被转换为自定义下拉框并隐藏原生元素，导致绑在原生 `<select>` 上的提示**用户永远看不到**。现在 `convertSelect` 会把 `title`/`data-tip` 转移到可见的 `.cdd-trigger` 上；`bindTooltip` 同时兼容 `title` 与 `data-tip` 两种来源。**所有**带提示的下拉框一并受益。
2. `style.css` 的 `.cdd-tip` 原为 `white-space:nowrap; max-width:240px`，长提示会溢出背景。改为 `white-space:pre-line; word-break:break-word; max-width:min(280px, calc(100vw - 16px))` —— 长提示按 `\n` 分行并自动折行，短提示仍是单行。

**v4.1 实测**：`.cdd-trigger` 的 `data-tip` 含 3 段模型说明；悬浮后 `.cdd-tip` 实测 280×133px 多行渲染、`white-space=pre-line`、无溢出；无 JS 报错。
